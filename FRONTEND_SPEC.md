# ReActions – Frontend Integration Spec

This document defines **how the frontend should interact with the ReActions backend** over WebSockets.

The backend is **server-authoritative**.
The frontend is responsible only for:

* rendering UI
* sending user intents
* reacting to server events

---

## 1. Connection Details

### WebSocket URL

```text
ws://<backend-host>:8080
```

Example (local):

```text
ws://localhost:8080
```

---

## 2. Connection Lifecycle

### On connect

The frontend should:

* open a WebSocket connection
* wait for `CONNECTED` message

```json
{
  "type": "CONNECTED"
}
```

No authentication is required.

---

## 3. General Message Format

### Client → Server

```json
{
  "type": "ACTION_TYPE",
  "payload": { ... }
}
```

### Server → Client

```json
{
  "type": "EVENT_TYPE",
  "payload": { ... }
}
```

* `type` is always a **string**
* `payload` structure depends on the message

---

## 4. Player Identity

* `playerId` is generated by the backend
* Frontend must **store it in memory**
* Frontend must **never generate or modify it**

The backend identifies players by their WebSocket connection.

---

## 5. Room Entry Flows

Frontend must choose **one of three entry paths**.

---

### 5.1 Create Room (Invite Flow)

#### Client → Server

```json
{
  "type": "CREATE_ROOM",
  "payload": {
    "name": "PlayerName"
  }
}
```

#### Server → Client

```json
{
  "type": "ROOM_CREATED",
  "payload": {
    "roomId": "uuid",
    "roomCode": "1234",
    "playerId": "uuid"
  }
}
```

#### Frontend behavior

* Display `roomCode` to the user
* Show “Waiting for opponent…”
* Keep socket open

---

### 5.2 Join Room by Code

#### Client → Server

```json
{
  "type": "JOIN_BY_CODE",
  "payload": {
    "name": "PlayerName",
    "code": "1234"
  }
}
```

#### Success Response

```json
{
  "type": "JOINED",
  "payload": {
    "roomId": "uuid",
    "playerId": "uuid"
  }
}
```

#### Error Response

```json
{
  "type": "ERROR",
  "payload": {
    "message": "Invalid or expired room code"
  }
}
```

#### Frontend behavior

* On success → transition to game screen
* On error → show message and allow retry

---

### 5.3 Matchmaking (Random Opponent)

#### Client → Server

```json
{
  "type": "FIND_MATCH",
  "payload": {
    "name": "PlayerName"
  }
}
```

#### Waiting Response

```json
{
  "type": "MATCH_WAITING",
  "payload": {
    "message": "Waiting for opponent..."
  }
}
```

#### Match Found

```json
{
  "type": "JOINED",
  "payload": {
    "roomId": "uuid",
    "playerId": "uuid"
  }
}
```

#### Frontend behavior

* Show loading / waiting UI
* Automatically transition when JOINED arrives

---

## 6. Game Lifecycle Events

The frontend **does not control game flow**.
It reacts to server events only.

---

### 6.1 Game State Update

```json
{
  "type": "GAME_STATE",
  "payload": {
    "state": "COUNTDOWN | PROMPT | RESULT | FINISHED"
  }
}
```

Frontend should:

* update UI state
* disable invalid inputs

---

### 6.2 Prompt Event

```json
{
  "type": "PROMPT",
  "payload": {
    "round": 1,
    "prompt": {
      "type": "CLICK_NOW"
    }
  }
}
```

Frontend should:

* render the prompt immediately
* enable user input
* start client-side animation/timer (visual only)

---

### 6.3 Player Action

When user reacts (click / key press):

```json
{
  "type": "PLAYER_ACTION",
  "payload": {}
}
```

Notes:

* No timing info required
* Backend calculates reaction time
* Frontend should **send once per round**

---

### 6.4 Round Result

```json
{
  "type": "ROUND_RESULT",
  "payload": {
    "winnerPlayerId": "uuid",
    "scores": [
      { "playerId": "uuid", "score": 3 },
      { "playerId": "uuid", "score": 2 }
    ]
  }
}
```

Frontend should:

* show round winner
* update scoreboard
* disable inputs until next prompt

---

### 6.5 Game Over

```json
{
  "type": "GAME_OVER",
  "payload": {
    "winnerPlayerId": "uuid"
  }
}
```

Frontend should:

* show final result
* offer “Play again” or exit

---

## 7. Error Handling

### Generic Error

```json
{
  "type": "ERROR",
  "payload": {
    "message": "Human readable error"
  }
}
```

Frontend should:

* display message
* keep socket alive unless explicitly disconnected

---

## 8. Disconnect Behavior (Current)

Current backend behavior:

* No reconnect support yet
* Disconnect ends the session implicitly

Frontend should:

* handle socket close
* show “Connection lost”
* allow refresh / retry

(Reconnect handling is planned but not implemented yet.)

---

## 9. Important Frontend Rules

* ❌ Do not assume game state
* ❌ Do not calculate winners
* ❌ Do not trust client timing
* ✅ Treat backend as source of truth
* ✅ UI state should mirror server events

---

## 10. Recommended Frontend State Model

Suggested high-level states:

* `DISCONNECTED`
* `CONNECTED`
* `WAITING_FOR_MATCH`
* `WAITING_IN_ROOM`
* `COUNTDOWN`
* `IN_ROUND`
* `ROUND_RESULT`
* `GAME_OVER`

---

## 11. Summary

Frontend responsibilities:

* User input
* UI rendering
* WebSocket messaging
* State transitions based on server events

Backend responsibilities:

* Room assignment
* Matchmaking
* Game rules
* Timing & scoring
